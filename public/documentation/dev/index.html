What This App Does

The Nail Salon App is a comprehensive salon management system designed to handle the day-to-day operations of a nail salon business. It manages the full lifecycle from customer walk-in or booking through service delivery, payment processing, and technician payroll.

Purpose & Goals

  • Replace manual paper-based tracking with a digital appointment and payment system
  • Automate technician commission calculation and payout tracking
  • Provide real-time visibility into salon operations (waiting list, tickets, calendar)
  • Integrate with GoHighLevel (GHL) CRM for customer and appointment synchronization
  • Support customer loyalty via credits, coupons, and gift cards

Setup Instructions

Prerequisites

  • PHP 8.2 or higher
  • Composer (PHP package manager)
  • MySQL 5.7+ or 8.0+
  • XAMPP, WAMP, Laravel Valet, or similar local development environment

Quick Setup (Automated)

# Clone the repository
git clone <repository-url> nailsalon-app
cd nailsalon-app

# Run the automated setup (installs deps, copies .env, generates key, runs migrations, builds assets)
composer setup

Manual Setup (Step by Step)

# 1. Install PHP dependencies
composer install

# 2. Copy environment file and generate app key
cp .env.example .env
php artisan key:generate

# 3. Create the MySQL database
mysql -u root -e "CREATE DATABASE nailsalon_app;"

# 4. Update .env with your database credentials (see Environment Variables section)

# 5. Run database migrations
php artisan migrate

# 6. Create the storage symlink (for file uploads)
php artisan storage:link

# 7. Install Node.js dependencies
npm install

# 8. Build frontend assets
npm run build

Running the Project Locally

# Option 1: Using the dev script (starts server + queue + vite concurrently)
composer dev

# Option 2: Manual start (run each in separate terminals)
php artisan serve              # Laravel dev server at http://localhost:8000
php artisan queue:listen       # Process background jobs
npm run dev                    # Vite dev server with hot reload
Note: If running via XAMPP, point the Apache document root to the public/ directory. The app URL will be http://localhost/nailsalon-app/public.

Running Tests

composer test
# or directly:
php artisan test

Features Overview

1. Dashboard

Role-aware control center showing daily stats (customer count, active technicians, tickets by status), latest tickets widget, and quick action shortcuts. Technicians see a simplified view with their own stats and clock-in/out controls.

2. Appointment Management

Supports both walk-in and booked appointment types. Multiple technicians can be assigned per appointment. Status lifecycle: waiting → in-progress → unpaid → paid (or cancelled / refunded). Includes no-show tracking.

3. Calendar View

Dual-view calendar (grid and technician list layout). Supports drag-and-drop rescheduling. Appointments color-coded by status. Unassigned appointments appear in "Not Assigned" column.

4. Waiting List

Queue management for walk-in and booked customers. Filter by type, search by name, assign technicians, and move to ticket workflow.

5. Tickets

Active service/payment records. Filterable by status tabs (Unpaid / Paid / Cancelled / Refunded). Each ticket tracks services, quantities, unit prices, and assigned technicians.

6. Payment Processing

Flexible payment breakdown supporting: subtotal, discount, customer credits, gift cards, tax, and tip. Tips are split per technician. Commission auto-calculated. Supports refunds with notes. Payment IDs are random strings (not auto-increment).

7. Customer Management

Customer profiles with visit history, contact information, profile photos, and credit balance. Credit ledger is immutable (append-only audit trail). GoHighLevel contact sync supported.

8. Technician Management

Staff profiles with commission/transaction history by date range. Clock in/out time tracking. Service count tracking for fair work distribution.

9. Turn Tracker

Real-time view of which technicians are clocked in and their service load. Configurable ordering rule (lowest-first or highest-first) for fair assignment.

10. Services & Categories

Service catalog with prices, descriptions, images, and color tags. Many-to-many relationship with service categories. Active/inactive toggle.

11. Coupons

Discount code system with percentage or fixed-amount discounts. Optional minimum order amount. Active/inactive toggle.

12. Gift Cards

Gift card issuance with PIN codes. Balance tracking (initial value and current balance). Applied during payment checkout.

13. Customer Credits

Loyalty point system configurable as fixed-unit or percentage-based earning. Credits can be earned and redeemed during payment. Full audit trail via immutable ledger.

14. Payout Reports

Technician earnings summary showing commissions, tips, and totals by date range. Used for payroll processing.

15. User Management

Staff account CRUD with role assignment. Admin can impersonate other users ("Login As") for troubleshooting. Active/inactive status control.

16. Settings

Key-value configuration store for: tax rate, currency, commission rates, credit earning rules, business info, logo, and GoHighLevel integration tokens.

17. GoHighLevel (GHL) Integration

Bidirectional sync with GoHighLevel CRM. OAuth-based authentication with hourly token refresh. Syncs contacts and appointments. Webhook handlers for incoming data. Non-blocking (failures logged, never interrupt main flow).

18. Online Check-In

Public-facing pre-appointment form. Customers can submit their name, phone, and notes without authentication.

19. In-App Documentation

Role-based user guide accessible within the application. Separate instructions for Admin, Receptionist, and Technician roles.

Authentication

How Authentication Works

The app uses a custom session-based authentication system (not Laravel Sanctum or Passport). Authentication state is stored in the server-side session.

Login Flow

  1. User submits POST /login with email/username + password
  2. System queries users table by email or username
  3. Password verified with Hash::check() (bcrypt, 12 rounds)
  4. On success, session keys are set:
    • salon_authenticated = true
    • salon_user_email = user's email
    • salon_role = user's role
  5. last_login_at timestamp updated on user record
  6. User redirected to /dashboard

Middleware: EnsureSalonAuthenticated

Applied to all protected routes. Checks for salon_authenticated session key. Returns:

  • Web requests: Redirects to /login
  • API requests: Returns 401 Unauthorized JSON

Admin Impersonation

Admins can "Login As" another user via POST /api/salon/users/{user}/login-as. The original admin's credentials are preserved in:

  • salon_impersonator_email
  • salon_impersonator_role

Impersonation ends via POST /impersonation/stop, restoring the original session.

API Documentation

Overview

All API endpoints are defined in routes/web.php (not a separate api.php). They are grouped under two prefixes:

PrefixAuth RequiredPurpose
/api/salon/*Yes (salon.auth)CRUD operations for all entities
/api/salon/data/*NoRead-only data endpoints

Authentication Method

All protected endpoints use session-based authentication via the salon.auth middleware. The session cookie is sent automatically by the browser. For API-style access, ensure the request includes the session cookie and CSRF token.

Response Format

All API responses return JSON. Successful operations return:

{
    "success": true,
    "message": "Operation completed successfully",
    "data": { ... }
}

Validation errors return 422 with Laravel's standard error format:

{
    "message": "The given data was invalid.",
    "errors": {
        "field_name": ["Error message"]
    }
}

Business Logic / Core Flows

Walk-In Customer Flow

  1. Customer arrives

    Receptionist opens the Waiting List screen.

  2. Create or select customer

    Search existing records, or add a new customer on the fly.

  3. Create appointment

    type: walk-in status: waiting

  4. Add services & assign technician(s)

    Select one or more services and assign the technicians who will perform them.

  5. Service begins

    Technician starts work status: in-progress

  6. Move to Tickets

    Service complete, ready for checkout status: unpaid

  7. Process payment

    Collect payment and close out the visit status: paid

Booking Flow

  1. Customer books appointment

    Booking comes in via the in-app Calendar or through GoHighLevel.

  2. Create appointment

    type: booked status: waiting appointment_datetime set

  3. GHL Sync (if configured)

    Non-blocking: creates the matching event in the GHL calendar. Failures are logged and do not abort the booking.

  4. Continue with walk-in flow

    From technician assignment onward, the booked appointment follows the same lifecycle as a walk-in: assign → in-progress → unpaid → paid.

Payment Flow

  1. Start from an unpaid ticket

    Ticket is in status: unpaid

  2. Open Pay / Checkout

    Review services, quantities, technicians, and subtotal before collecting payment.

  3. Apply adjustments
    • Discount (coupon code)
    • Customer credits
    • Gift card
    • Tax (from settings)
    • Tip (split per technician)
  4. Commit in a single DB transaction
    1. Create Payment record
    2. Update appointment status
    3. Update technician pivot (tip, commission, totals)
    4. Deduct customer credits
    5. Deduct gift card balance
    6. Award new credits (earned)
    7. Sync to GHL (non-blocking)
  5. Payment complete

    Ticket moves to status: paid

Critical: Payment and credit operations use lockForUpdate() for database-level concurrency control. This prevents race conditions when multiple users attempt to process the same payment simultaneously.

Customer Credits Flow

How credits are triggered

Manual

Admin adjusts via API.

POST /api/salon/customers/{id}/credits

add subtract set

Automatic

Earned during payment based on settings:

  • credit_earning_type = "fixed_unit" — fixed credits per transaction
  • credit_earning_type = "percentage" — % of subtotal

Transaction steps (all operations)

  1. Lock customer record

    Uses lockForUpdate() to prevent concurrent writes.

  2. Calculate new balance

    Apply the operation against current balance.

  3. Insert into customer_credit_ledgers

    Immutable audit row for the adjustment.

  4. Update customer.credit_balance

    Write the new running balance.

  5. Commit transaction

    All writes succeed together or roll back together.

GoHighLevel (GHL) Integration Flow

OUTBOUND App → GHL

  1. Appointment created, updated, or deleted

    Trigger fires from the local appointment event.

  2. GoHighLevelService::syncAppointment()

    Orchestrates the outbound call.

  3. Resolve GHL contact
    • findGhlContact() — look up by phone / email
    • otherwise createGhlContact()
  4. Push appointment to GHL
    • createGhlAppointment() on create/update
    • deleteGhlAppointment() on delete
Fault tolerance: All outbound calls are wrapped in try/catch. Failures are logged but never thrown — GHL sync will never block a local appointment.

INBOUND GHL → App

Customer sync

POST /api/customers/update/{ghl_id}

→ SalonCustomerController@syncFromGhl

Updates the local customer record.

Appointment webhook

POST /api/appointments/webhook/create

→ SalonAppointmentController@webhook

Creates a local appointment from the GHL event.

TOKEN REFRESH

  • Scheduled hourly via routes/console.php.
  • Runs the clickaio:refresh-token Artisan command.
  • Refreshes OAuth tokens stored in the settings table.

Web Server Configuration

Apache (.htaccess)

The public/.htaccess file is included. Ensure mod_rewrite is enabled and the document root points to /var/www/nailsalon-app/public.

Nginx

server {
    listen 80;
    server_name your-domain.com;
    root /var/www/nailsalon-app/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.2-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        include fastcgi_params;
    }

    location ~ /\.(?!well-known).* {
        deny all;
    }
}

Queue Worker

The app uses a database queue. Set up a process manager to keep the worker running:

# Supervisor config (/etc/supervisor/conf.d/nailsalon-worker.conf)
[program:nailsalon-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/nailsalon-app/artisan queue:work --tries=3 --timeout=90
autostart=true
autorestart=true
numprocs=1
user=www-data
redirect_stderr=true
stdout_logfile=/var/www/nailsalon-app/storage/logs/worker.log

Scheduler (Cron)

Add this cron entry for the Laravel scheduler (handles hourly GHL token refresh):

* * * * * cd /var/www/nailsalon-app && php artisan schedule:run >> /dev/null 2>&1

Maintenance Notes

Things to Watch Out For

1. GoHighLevel Token Expiry

The GHL OAuth token is refreshed hourly via a scheduled command. If the scheduler cron job stops running, the token will expire and all GHL sync operations will silently fail. Check storage/logs/laravel.log for GHL-related errors.

2. Database Queue

The app uses a database-backed queue. The jobs table can grow large over time. Monitor and prune failed jobs periodically:

php artisan queue:prune-failed --hours=168  # Remove failed jobs older than 7 days

3. Session Table

With the long session lifetime, the sessions table can accumulate stale records. Consider periodic cleanup:

DELETE FROM sessions WHERE last_activity < UNIX_TIMESTAMP(NOW() - INTERVAL 30 DAY);

4. Payment ID Generation

Payment IDs are random strings. While collision probability is extremely low, monitor for any duplicate key errors in logs.

5. Financial Precision

All monetary values use decimal(12,2) or decimal(10,2). Never change these to float or double types. Eloquent casts are configured to maintain decimal precision.

6. Credit Ledger Immutability

The customer_credit_ledgers table has no updated_at column by design. Records are append-only. Never update or delete ledger entries — create corrective entries instead.

7. Cache / Config Clearing

After deploying changes to config or routes:

php artisan config:cache
php artisan route:cache
php artisan view:cache

8. Storage Link

The public/storage symlink must exist for file uploads to be accessible. If it breaks after deployment, recreate it:

php artisan storage:link
